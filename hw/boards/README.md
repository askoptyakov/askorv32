Платы (платформы) askoRV32
===========================

Один проект — несколько отладочных плат. Ядро, `cpu.sv`, периферия (`hw/src`) и программа (`fw/Core`) общие; у каждой платы — своя ПЛИС, свои выводы и свой проект Gowin.

| Плата | ПЛИС | Корпус | Флеш конфигурации | Программатор / UART |
|---|---|---|---|---|
| **Tang Nano 9K** | GW1NR-LV9QN88PC6/I5 (GW1NR-9C) | QFN88 | встроенная flash + внешняя P25Q32U 4 МБайт (MSPI при MODE1 = 1) | BL702: JTAG + UART (выводы 17 TX, 18 RX) |
| **Tang Primer 20K** (Dock) | GW2A-LV18PG256C8/I7 (GW2A-18C) — ПЛИС реального проекта | PBGA256 | только внешняя SPI-флеш 8 МБайт (MSPI, загружается всегда из неё) | BL616: JTAG + UART (M11 TX, T13 RX) |

## Tang Nano 9K: переключатель MODE1

Способ загрузки задаёт вывод 87 (MODE1): 0 — AUTO BOOT (встроенная flash), 1 — MSPI (внешняя флеш). Режим в конфигураторе должен совпадать с положением переключателя: MODE1 = 0 — блок SPIFLASH «в SRAM или встроенной flash» и запуск «riscv FPGA Flash»; MODE1 = 1 — «в этой флеш, загрузка по MSPI» и «riscv SPI-FLASH».

Вывод MODE1 нельзя оставлять висящим. 2026-10-03 при сломанном резисторе подтяжки к 0 ПЛИС фактически работала в MSPI: при включении и после перезагрузки по JTAG грузилась из внешней флеш, а запись во встроенную flash кончалась **CRC FAIL** (openFPGALoader после записи перезагружает ПЛИС и сверяет USERCODE — пришёл USERCODE конфигурации из внешней флеш). Проверить, какая конфигурация работает: USERCODE (по умолчанию равен `//CheckSum` из заголовка `.fs`) — `openocd -c "set JTAG_ONLY 1" -f fw/boards/tangnano9k/openocd.cfg -c "init; irscan gw1nr9.cpu 0x13; echo [drscan gw1nr9.cpu 32 0]; shutdown"`. Флажок Multi_Boot в настройке процесса Gowin на битовый поток GW1NR-9 не влияет (проверено).

Проверено на 9K после переноса (2026-10-03): SRAM, отладка (`restore`, `main`, шаг), внешняя флеш в MSPI (3 мин 6 с), встроенная flash в AUTO BOOT (12.5 с, CRC Success, старт по питанию).

## Где что лежит

```
hw/src/                          общие исходники: ядро, cpu.sv, память, отладчик, периферия
hw/boards/<плата>/riscv.gprj     проект Gowin EDA платы (исходники - ../../src, файлы платы - рядом)
hw/boards/<плата>/top.sv         верхний уровень      } создаёт конфигуратор (sw/socgen),
hw/boards/<плата>/riscv.cst      назначение выводов   } вручную не правятся
hw/boards/<плата>/riscv.sdc      временные ограничения (правится вручную; порт кварца подставляет генератор)
hw/boards/<плата>/impl/          результаты Gowin: impl/pnr/riscv.fs (битовый поток), riscv.posp,
                                 riscv_process_config.json (настройка процесса; MSPI/SSPI/READY/DONE, VCC,
                                 Place_Option, Loading Rate выставляет генератор)
fw/Core/                         общая программа: драйверы, start.S, main.c
fw/boards/<плата>/<плата>.gwsoc  конфигурация ПЛИС платы - её открывает конфигуратор
fw/boards/<плата>/soc.h          описание ПЛИС для программы (создаёт конфигуратор)
fw/boards/<плата>/openocd.cfg    отладчик OpenOCD для этой платы
fw/<КонфигурацияСборки>/         выход сборки Eclipse: riscv.elf, riscv.bin, riscv.fs (программа, влитая mergetool)
```

`<плата>` — `tangnano9k`, `tangprimer20k` (как у `openFPGALoader -b`). Конфигурации сборки Eclipse — `TangNano9K`, `TangPrimer20K`: имя конфигурации без учёта регистра совпадает с именем платы.

В `.gwsoc` плату описывает раздел `board`, кристалл — `device`, каталоги — `paths`:

```json
"board": { "id": "tangprimer20k", "title": "Tang Primer 20K", "buildConfig": "TangPrimer20K", "loader": "tangprimer20k" },
"device": "GW2A-LV18PG256C8/I7",
"paths": { "hw": "../../../hw/boards/tangprimer20k", "src": "../../../hw/src", "top": "top.sv", "cst": "riscv.cst",
           "soc": "soc.h", "generator": "../../../sw/socgen/socgen.py" }
```

Свойства кристаллов (выводы корпуса, пределы rPLL, число блоков BSRAM, встроенная flash, выводы двойного назначения, VCC) — в `sw/socgen/web/devices.js`, его создаёт `sw/socgen/mkdevices.py` из файлов Gowin IDE. Их читают и конфигуратор, и генератор, и `fpgaload.py`.

## Переключение платы в Eclipse

**Project → Build Configurations → Set Active → TangNano9K / TangPrimer20K** (или список у молотка на панели). От активной конфигурации зависит всё:

- сборка: свой `soc.h` (`-I boards/<плата>`), свой каталог `fw/<конфигурация>`, после сборки mergetool вливает программу в битовый поток своей платы `hw/boards/<плата>/impl/pnr/riscv.fs`;
- запуски `riscv FPGA SRAM`, `riscv FPGA Flash`, `riscv SPI-FLASH` передают в `sw/fpgaload/fpgaload.py` ключ `--config ${config_name:riscv}`: плата, битовый поток, `openFPGALoader -b <плата>` и каталог программы берутся из её `.gwsoc`;
- отладка `riscv Debug OpenOCD`, `riscv Debug SPI-FLASH`: программа `${config_name:riscv}/riscv.elf`, OpenOCD — `fw/boards/${config_name:riscv}/openocd.cfg` (Windows не различает регистр букв в путях).

Конфигуратор (двойной щелчок по `.gwsoc` или кнопка «Конфигуратор ПЛИС») и окно «Программатор ПЛИС» работают с выбранной платой: если плат несколько, команда спросит, какую открыть (или возьмёт выделенный `.gwsoc`). Обе ПЛИС проекта собираются независимо — проекты Gowin и битовые потоки у плат свои.

Смена ПЛИС самой платы — список ПЛИС в шапке конфигуратора (два варианта: GW1NR-9 и GW2A-18). Номера выводов у корпусов разные (QFN — 1…88, BGA — «H11»), поэтому назначения, которых нет в новом корпусе, снимаются, а выводы флеш SPIFLASH встают на выводы MSPI нового кристалла. Кристалл проекта Gowin (`riscv.gprj`, элемент `Device`), напряжение ядра VCC и `PLL_DEVICE` в `top.sv` генератор выставляет сам.

## Новая плата

1. Скопировать `hw/boards/<похожая плата>` (без `impl/*` кроме `riscv_process_config.json`) и `fw/boards/<похожая плата>`, переименовать `.gwsoc`, поправить в нём `board` и `paths.hw`.
2. ПЛИС другая — добавить её в `FAMILIES` в `sw/socgen/mkdevices.py` и запустить его. Раскладку битового потока для mergetool — найти пробными сборками (`sw/mergetool/fsprobe`, описание — `sw/mergetool/README.md`).
3. Конфигуратор: кварц, сброс, выводы периферии, банки VCCIO; «Собрать».
4. `fw/boards/<плата>/openocd.cfg` — IDCODE ПЛИС (`openFPGALoader -b <плата> --detect`).
5. Eclipse: конфигурация сборки — копия существующей (**Manage Configurations → New → Copy settings from**), имя = `board.buildConfig`; в ней поменять путь `boards/<плата>` в Include paths и пути `in_fpga`, `in_bsram_location` в Build Variables (Properties → C/C++ Build → Build Variables).

## Несколько плат на одном ПК

Платы можно подключить одновременно и работать с ними параллельно: загружать одну, пока другая на отладке, читать оба UART. Программаторы Tang Nano 9K (BL702) и Tang Primer 20K (BL616) для ПК одинаковые — FTDI-совместимые `0403:6010` с одним именем и даже одним серийным номером (`FACTORYAIOT_PRO`), поэтому openFPGALoader и OpenOCD сами их не различают. Различает ПЛИС на плате: IDCODE по JTAG (GW1NR-9 — `0x1100481b`, GW2A-18 — `0x0000081b`, поле `idcode` в `sw/socgen/web/devices.js`).

- **`sw/fpgaload/boardsel.py`** перечисляет программаторы через `libusb-1.0.dll` (та же, что у openFPGALoader: шина, адрес, путь порта `шина-порт`), при нескольких — читает IDCODE за каждым (`openFPGALoader --busdev-num <шина:адрес> --detect`) и выбирает программатор платы. IDCODE запоминается в `%TEMP%\askorv32_probes.json` (по шине, адресу и порту: при переподключении адрес меняется, старый кэш не мешает). Один программатор — ничего не опрашивается. `py sw/fpgaload/boardsel.py --list` — все программаторы и ПЛИС на них.
- **`fpgaload.py`** (запуски «riscv FPGA SRAM / Flash / SPI-FLASH», окно «Программатор ПЛИС») передаёт openFPGALoader `--busdev-num`. «Программатор занят»: при одном программаторе — если запущен любой OpenOCD; при нескольких — только если запущен OpenOCD **этой** платы.
- **`fw/boards/<плата>/openocd.cfg`** при запуске OpenOCD вызывает `boardsel.py --openocd` (нужен Python, команда `py`) и выполняет `adapter usb location <шина-порт>`. Номер своего процесса OpenOCD пишет в `%TEMP%\askorv32_openocd_<порт>.pid` — по нему fpgaload и boardsel видят, что программатор занят, и не трогают его (чужой доступ сбивает USB-соединение OpenOCD).
- **Отладка двух плат в Eclipse одновременно**: запуск «riscv Debug OpenOCD» берёт плату активной конфигурации, а порты у него фиксированные (GDB 3333, Telnet 4444, TCL 6666). Для второй платы нужна копия запуска с другими портами (например, 3334/4445/6667) и явной платой: программа `TangPrimer20K/riscv.elf`, конфиг `boards/TangPrimer20K/openocd.cfg`.
- **UART**: у каждой платы свой интерфейс B программатора. С включённым Load VCP — два COM-порта (какой чей — по Диспетчеру устройств: «Расположение» содержит номер порта USB, тот же, что у `boardsel.py --list`). Через FTDI D2XX номер видно в `LocId`: `0x2P2` — шина 2, порт P.

Проверено 2026-10-03: обе платы подключены одновременно (9K — порт 2-4, 20K — порт 2-3); пока OpenOCD отлаживал 20K (14 остановов подряд), 9K загружалась в SRAM (CRC Success); загрузка 20K в это время получила отказ «занят … PID»; сессия OpenOCD 20K прошла без ошибок; запись во внешнюю флеш обеих плат шла параллельно; оба UART читались одновременно.

## Tang Primer 20K

Распиновка сверена по схемам Dock rev 3714 (Tang_Primer_20K_Dock_3714) и SOM 3961; у старых ревизий Dock (и в LiteX) часть кнопок и переключателей разведена иначе.

| Назначение | Вывод | Примечание |
|---|---|---|
| Кварц 27 МГц | H11 | GCLKT_0 |
| Сброс (кнопка S1 «Key_0», активный 0) | T10 | FPGA_RST: к нему же подключён супервизор питания SGM803; это вывод SSPI (SI) - генератор включает «SSPI как обычные I/O» |
| LED0…LED5 (горят нулём) | C13, A13, N16, N14, L14, L16 | C13 = DONE, A13 = READY — генератор включает «DONE/READY как обычные I/O» |
| UART программатора: TX / RX ПЛИС | M11 / T13 | интерфейс B BL616 |
| SPI-флеш: SCK, CS#, MOSI, MISO | L10, M9, R10, P10 | выводы MSPI; JEDEC ID 0x0B4017 — XTX 64 Мбит (8 МБайт), хотя на схеме подписан XT25B32 |
| JTAG ПЛИС | A7 TCK, B8 TMS, A6 TDI, C6 TDO | заняты отладчиком (GW_JTAG), в `.cst` не назначаются |
| Кнопки Key_1…Key_3 | T3, T2, D7 | банки 4, 6 — 1,5 В |
| Key_4 | B10 | **RECONFIG_N** — нажатие перезагружает ПЛИС |

Банки VCCIO: 0–3 и 7 — 3,3 В; 4–6 — 1,5 В (DDR3).

**DIP-переключатель и RECONFIG_N.** Если ПЛИС не загружается ни из флеш, ни по JTAG (горят LED0 и LED1 — DONE и READY низкие; openFPGALoader зависает на «Erase SRAM», регистр состояния 0x20, команда CONFIG_ENABLE не действует) — вывод RECONFIG_N прижат к земле. На Dock это делает 5-позиционный DIP-переключатель (в части ревизий SW0 и KEY4 поменяны местами, и B10 идёт на переключатель): перевести движки в другое положение и перезапитать плату. Проверено 2026-10-02.

**UART.** Программатор BL616 («FactoryAIOT Pro JTAG Debugger») — двухканальный FTDI-совместимый: интерфейс A (JTAG) на драйвере WinUSB (openFPGALoader, OpenOCD), интерфейс B («USB Debugger B») — на драйвере FTDI. COM-порт появляется, если в свойствах интерфейса B (Диспетчер устройств → USB Serial Converter B → Дополнительно) включить **Load VCP**; без него UART читается через FTDI D2XX (`ftd2xx.dll`).

**Загрузка и отладка** (проверено на плате 2026-10-02, openFPGALoader v1.1.1, OpenOCD xPack 0.12.0-7):

| Действие | Время | Как |
|---|---|---|
| Битовый поток в SRAM | 3.9 с | `fpgaload.py sram --config TangPrimer20K` (с программой, влитой mergetool, — 5.2 с) |
| Битовый поток (882 кБайт) во внешнюю флеш | 9 с | `fpgaload.py spiflash` — у GW2A быстрый путь записи через JTAG (у GW1N тот же поток пишется 176 с) |
| Образ программы во флеш (0x100000) + перезапуск | 1.5 с | там же |
| Чтение флеш | ~100 кБайт/с | `openFPGALoader --dump-flash` |
| Отладка | — | OpenOCD: TAP IDCODE 0x0000081b, IR 8 бит, `dtmcs` = 0x00001071 (первое чтение после загрузки по JTAG — 0, как на 9K); halt, регистры, память, `reset halt` после загрузки из флеш |

Встроенной flash у GW2A нет: «riscv FPGA Flash» и «Очистить встроенную flash» для этой платы отключены. Битовый поток GW2A-18 — 882 кБайт (до 0x0DC81E), поэтому образ программы во флеш — не ниже 0x100000 (конфигуратор проверяет).

**Свободные выводы и TM1638.** Многие выводы SOM на Dock уже чем-то заняты. Индикатор TM1638 подключён к T9 (STB), P8 (CLK), T7 (DIO), подписанным на Dock, и работает. Но T9 — это ещё и вход данных RGB-светодиода WS2812 (он горит случайным цветом от посылок STB), а P8 и T7 — линии MIC_DAT0 и MIC_DAT3 разъёма микрофонной решётки (без неё не мешают). Назначая выводы в конфигураторе, сверяйтесь со схемой Dock: DIO/CLK/STB в `.gwsoc` должны совпадать с проводами.

**СИФУ (блок SIFU) на Dock.** Входы платы синхронизации NSB — разъём PMOD **J6**, контакты 5–10: B12 (AB), C12 (BA), B13 (BC), A14 (CB), B14 (CA), A15 (AC); импульсы VS1…VS6 — PMOD **J5**, контакты 5–10: L9, N8, N9, N7, N6, D11. Это линии разъёма RGB-LCD (без LCD свободны); на J5 импульсы удобно смотреть осциллографом. Банки 3 и 7 — 3,3 В: высокий уровень NSB (≈ 1,8 В) для них мал — [periph/sifu/README.md, «Плата синхронизации NSB»](../src/periph/sifu/README.md#плата-синхронизации-nsb). На Tang Nano 9K СИФУ стоит на выводах 79–84 (входы, банк 3 — 1,8 В) и 28–33 (выходы).

**Tang Primer 20K: зависание программатора при записи внешней флеш (2026-10-03, причина найдена).** `fpgaload.py spiflash` (openFPGALoader, `--external-flash`) на части битовых потоков обрывается: `Error: ftdi_read_data in mpsse_read`, перед этим молча пишет во флеш мусор, после — программатор BL616 не отвечает до переподключения USB. Флеш и ПЛИС исправны.

**Причина.** У GW2A openFPGALoader пишет флеш через мост JTAG→SPI (команда `0x16`): страница — один сдвиг DR, последний байт уходит хвостом: 7 бит командой MPSSE `0x1B 0x06 <байт>` и последний бит вместе с TMS (`0x4B 0x00 0x01/0x81`). Программатор BL616 (эмуляция FT2232) зависает, когда байт данных этой 7-битной команды равен `0x71` — то есть когда **последний байт страницы — `0x8E`** (порядок бит обратный). Проверено поиском делением: страница из `0xFF` с последним байтом `0x8E` вешает программатор по любому адресу; `0x0E` (`0x70`) и `0x8F` (`0xF1`) — нет; тот же байт внутри страницы безвреден. В потоке 2 октября таких страниц нет (он и сейчас пишется за 9 с), в сегодняшних — по одной (BSRAM: `0x31200`, LUT: `0x5FB00`), ровно в местах сбоев. Испорченный недописанный поток ПЛИС потом грузила с `Done Final`, отладчик и JTAG с ним сбоили — отсюда «перестало работать всё».

**Исправлено** в `sdk/openfpgaloader` (`bl616_bitmode_tail.patch`, [подробно](../../sdk/openfpgaloader/README.md#программатор-bl616-зависание-на-записи-флеш-gw2a-bl616_bitmode_tailpatch-1-файл-215-строк)): остаточные биты длинного сдвига записи передаются по одному, байт данных битовой команды — только `0x00`/`0x01`. Проверено: `fpgaload.py spiflash --force` с «опасным» потоком — 9.6 с, сверка через процессор — 0 расхождений, загрузка из флеш и отладка работают; на 9K запись флеш не замедлилась (3 мин 3 с). Запасной путь без openFPGALoader — запись контроллером SPIFLASH процессора через OpenOCD (1 мин 50 с).

**Регистровый файл на BSRAM** — у 20K включён («Процессор» → «Регистровый файл: BSRAM, чтение по спаду», `core.rfType = "bsram"`, `RF_TYPE = 2`): −228 LUT, +2 блока BSRAM из 46, Fmax 66–68 МГц при любом Place. На 9K остаётся LUT: 45.5 МГц только при Place 1/2, при Place 0 — 41.5. Подробно — [performance_roadmap.md, шаги 21 и 22](../info/performance_roadmap.md#шаг-22-регистровый-файл-на-bsram-чтение-по-спаду-в-стадии-d-ч19).

**Ресурсы и частота** (Gowin 1.9.11, конвейер, M, отладчик, IMEM 16 / DMEM 8 кБайт, GPIO, STIM, UART, SPIFLASH): 5617 LUT из 20 736, 2140 регистров, BSRAM 12 из 46, DSP 2 из 24; **Fmax clk_core 65.6 МГц** при цели 50 МГц в `riscv.sdc` (на GW1NR-9 та же схема — 46–48 МГц). Рабочая частота пока та же, 45 МГц: запас позволяет её поднять (в конфигураторе — «Такт и сброс»; цель в `riscv.sdc` держать выше рабочей частоты).
