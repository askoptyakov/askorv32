SPIFLASH — внешняя SPI-флеш и загрузка программы
=================================================

Контроллер внешней флеш-памяти SPI (режим 0, однобитный SPI). Делает две вещи:

1. **Загрузчик программы.** После сброса системы держит ядро в сбросе, читает из флеш образ программы, проверяет его и копирует в IMEM и DMEM, затем отпускает ядро. Программу не нужно вливать в битовый поток ПЛИС: битовый поток записывается во встроенную flash один раз, а программа обновляется отдельно, во внешней флеш.
2. **Обмен с флеш из программы** — чтение, запись страниц, стирание, ID, состояние. Свободная часть флеш (всё, кроме области образа) — для параметров программы. Библиотека — `fw/Core/Inc/spiflash.h`.

| Файл | Назначение |
|---|---|
| `spiflash.sv` | модуль `spiflash_top`: регистры по шаблону `periph_regs`, приёмопередатчик SPI, загрузчик |
| `tb_spiflash.sv` | тест: `py hw/sim/run_periph_tests.py spiflash` |
| `sim/spiflash_model.sv` | модель микросхемы флеш для тестов (в проект ПЛИС не входит) |
| `fw/Core/Inc/spiflash.h`, `fw/Core/Src/spiflash.c` | библиотека на Си |
| `sw/bootimage/bootimage.py` | образ программы из ELF |
| `sw/fpgaload/fpgaload.py spiflash` | запись битового потока и образа во флеш через openFPGALoader (Eclipse: «riscv SPI-FLASH» или окно «Программатор ПЛИС») |
| `sw/fpgaload/fpgaload.py erase-spiflash` | стирание всей флеш (Eclipse: «Программатор ПЛИС» → «Очистить SPI-флеш») |
| `sdk/openfpgaloader` | openFPGALoader с ускоренной (в ~3.5 раза) записью и с очисткой внешней флеш GW1N |

Образец — PicoSoC (`spimemio.v`, [YosysHQ/picorv32](https://github.com/YosysHQ/picorv32/tree/main/picosoc)): там программа исполняется прямо из флеш (XIP), а ядро ждёт каждое слово. У askoRV32 у памяти команд нет ожидания (BSRAM, выборка за такт), и выборка из SPI стоила бы ~40 тактов на команду, поэтому программа копируется в BSRAM до старта ядра. От PicoSoC взяты: пробуждение флеш при старте (`0xFF`, затем `0xAB`), слово из 4 байт младшим байтом вперёд, ручной режим обмена (у PicoSoC — побитовый, здесь — побайтовый, с аппаратным сдвигом) и модель флеш для тестов.

## Подключение

Блок SPIFLASH в конфигураторе ПЛИС (`fw/riscv.gwsoc`): окно адресов — по умолчанию `0x1500_0000`, выводы SCK, CS#, MOSI, MISO, объём флеш, частота SCK, загрузка программы и адрес образа.

На Tang Nano 9K флеш U3 (PUYA P25Q32U, 4 МБайт) подключена к выводам **59** (SCLK), **60** (CS#), **61** (MOSI), **62** (MISO), банк 1, 3.3 В; WP# и HOLD# подтянуты к питанию. Это выводы MSPI ПЛИС (двойного назначения): чтобы занять их как обычные I/O, нужен флажок «Use MSPI as regular IO» в настройке Gowin EDA — генератор `socgen` ставит его сам (`"MSPI": true` в `hw/impl/riscv_process_config.json`, у apicula — ключ `--mspi_as_gpio`). Конфигурация ПЛИС у Tang Nano 9K — из встроенной flash, внешняя флеш для неё не используется.

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `MEMORY_TYPE` | 0 | 1 — данные чтения на следующем такте (шина с BSRAM), 0 — в том же такте |
| `DIV_INIT` | 1 | `DIV` после сброса: SCK = f_clk / (2 · (DIV + 1)); 1 — 11.25 МГц при 45 МГц |
| `BOOT_EN` | 1 | 1 — загрузчик (способ хранения «внешняя флеш, MSPI»); 0 — только обмен (загрузчик убирается синтезом, −270 LUT) |
| `BOOT_ADDR` | `24'h000000` | адрес образа во флеш |
| `BOOT_WORDS` | 16384 | предел образа, слов (64 кБайт); длиннее — ошибка разметки |
| `WAKE_CLKS` | 2048 | пауза после команды пробуждения `0xAB`, тактов (tRES1 флеш) |

| Порт | Смысл |
|---|---|
| `clk`, `rst` | такт и сброс шины периферии; сброс (кнопка, PLL, `ndmreset` отладчика) запускает загрузку |
| `Write`, `Read`, `Addr`, `WData`, `RData` | шина регистров; `Read` — строб чтения (автозапуск обмена в режиме `rdauto`) |
| `spi_sck`, `spi_cs_n`, `spi_mosi` | выходы SPI (из регистров) |
| `spi_miso` | вход SPI (через регистр) |
| `boot_hold` | 1 — держать ядро в сбросе (порт `boot_hold` процессора `cpu.sv`) |
| `boot_Write`, `boot_Addr`, `boot_WData` | запись загрузчика в память словами (порт `boot_*` процессора) |

**Проверено на плате** (01.10.2026, Tang Nano 9K): образ примера 7 записан openFPGALoader'ом (8 с вместе с перезапуском ПЛИС), загрузчик берёт его после перезапуска ПЛИС (`openFPGALoader -r`, как при включении питания) и после сброса отладчиком (`BOOT = 0x05CA_0001`); с чужими данными во флеш — `BOOT = 0x0001_0002` и программа из битового потока; JEDEC ID `0x856016`, запись и чтение параметров в свободной области; отладка программы из флеш — [hw/info/debug.md](../../../info/debug.md#программа-во-внешней-spi-флеш).

Загрузчик включается только в способе хранения «внешняя флеш, MSPI» (см. ниже), и только у одного блока SPIFLASH — у того, на чьей флеш лежит конфигурация ПЛИС. В способах SRAM и «встроенная flash», а также у других блоков SPIFLASH контроллер только обменивается с флеш (данные программы). В проверке 01.10.2026 конфигурация была во встроенной flash, а программа — во внешней флеш; этот промежуточный вариант больше не поддерживается.

Ресурсы (Gowin, синтез модуля): с загрузчиком 462 LUT, 246 регистров, 31 ALU; без загрузчика (`BOOT_EN = 0`) — около 190 LUT. Во всей ПЛИС (с мультиплексорами порта `boot_*` в `cpu.sv`) блок добавил 556 LUT и 247 регистров; Fmax ядра не ухудшилась (44.8/47.3/47.3 МГц при Place Option 0/1/2 против 44.1/45.6/45.6 без блока).

## Загрузка программы

После сброса загрузчик:
1. посылает `0xFF` (выход из непрерывного чтения) и `0xAB` (выход из глубокого сна), ждёт `WAKE_CLKS` тактов;
2. **проверка:** читает образ командой `0x03` с адреса `BOOT_ADDR` целиком — признак, адреса и длины сегментов, контрольную сумму — и ничего не пишет;
3. **копирование:** если всё сошлось, читает образ второй раз и пишет сегменты в IMEM (`0x00xx_xxxx`) и DMEM (`0x10xx_xxxx`);
4. отпускает ядро; итог — в регистре `BOOT`.

Если образа нет (флеш стёрта, признак не совпал), образ испорчен или разметка неверна, **память не трогается**: ядро стартует с тем, что в ней было, — после включения питания это программа из битового потока ПЛИС. Так плата с пустой флеш работает как раньше.

Время загрузки — два чтения образа: при SCK 11.25 МГц около 1.5 мс на кБайт образа (образ 8 кБайт — 13 мс, 48 кБайт — 75 мс). Всё это время ядро в сбросе, периферия уже сброшена и выключена.

**Отладчик.** Сброс отладчиком (`ndmreset`, команда `reset` OpenOCD) — такой же сброс системы: программа снова копируется из флеш. Пока идёт загрузка, модуль отладки показывает ядро недоступным (`dmstatus.allunavail`), OpenOCD ждёт; сброс с остановом (`reset halt`) останавливает ядро на первой команде уже загруженной программы (PC = 0). Загрузка программы отладчиком (GDB `restore`) идёт в память после сброса и флеш не меняет.

### Формат образа

32-битные слова, младший байт по младшему адресу флеш:

| Слово | Значение |
|---|---|
| 0 | признак `0x3156_5241` (байты `"ARV1"`) |
| | **сегмент:** адрес в памяти (кратен 4; `0x00xx_xxxx` — IMEM, `0x10xx_xxxx` — DMEM; смещение < 64 кБайт) |
| | число слов сегмента N (1..`BOOT_WORDS`) |
| | N слов данных |
| | … следующие сегменты … |
| | конец: адрес 0, число слов 0 |
| | контрольное слово: сумма **всех** слов образа вместе с ним по модулю 2³² равна 0 |

Образ собирает `sw/bootimage/bootimage.py` из ELF: загружаемые сегменты программы по их рабочим адресам (`.text` — в IMEM с 0, `.data` и `.rodata` — в DMEM с `0x1000_0000`); `.bss` обнуляет `start.S`. Обычный образ — два сегмента.

```
py sw/bootimage/bootimage.py fw/Debug/riscv.elf --imem-kb 16 --dmem-kb 8
riscv_flash.bin: 5932 Байт (IMEM 0x00000000 5544 Байт, DMEM 0x10000000 356 Байт)
```

## Три способа хранения конфигурации и программы

| Способ | Выводы MODE (Tang Nano 9K) | Где программа | Настройка блока SPIFLASH «Конфигурация и программа» | Запись (Eclipse / `fpgaload.py`) | Время |
|---|---|---|---|---|---|
| **SRAM** — до выключения питания | любые | в битовом потоке (BSRAM) | «в SRAM или встроенной flash» | «riscv FPGA SRAM» / `sram` | ~4 с |
| **встроенная flash** (AUTO BOOT) | MODE1 = MODE0 = 0 — как с завода | в битовом потоке | «в SRAM или встроенной flash» | «riscv FPGA Flash» / `flash` | ~12 с |
| **внешняя SPI-флеш** (MSPI) | MODE1 = 1 — подтяжка вывода 87 к 1.8 В | образом во флеш с `0x100000`, копирует загрузчик | «в этой флеш, загрузка по MSPI» | «riscv SPI-FLASH» / `spiflash` | ~3 с (только программа), ~3 мин (с битовым потоком) |

Настройка блока решает, как собирается ПЛИС: в первых двух способах загрузчик выключен (`BOOT_EN = 0`), флеш — только для данных программы; в третьем загрузчик включён и ждёт образ. Промежуточного варианта «конфигурация во встроенной flash, программа во внешней» нет. `fpgaload.py flash` при настройке «MSPI» отказывается работать (битовый поток собран для внешней флеш), `spiflash` при другой настройке — тоже. SRAM подходит для любой сборки: при сборке «MSPI» загрузчик после сброса возьмёт программу из образа во флеш, если он там есть.

Отладка во всех трёх способах одинакова ([hw/info/debug.md](../../../info/debug.md#программа-во-внешней-spi-флеш)): «riscv Debug OpenOCD» — с загрузкой программы в память (`restore`), «riscv Debug SPI-FLASH» — без загрузки, с той программой, что уже на плате.

## Конфигурация ПЛИС из этой же флеш (режим MSPI)

ПЛИС может брать битовый поток не из встроенной flash, а из внешней флеш — режим **MSPI** (выводы MODE = `010`). Тогда во внешней флеш лежит всё: конфигурация ПЛИС и программа. Так устроены ПЛИС без встроенной flash (GW2A и др.), и так возможно «тихое» обновление: программа пишет новую конфигурацию и программу во флеш, а при следующем включении питания стартует новая версия.

Подробная карта флеш (что где лежит, сколько свободно, как хранить параметры) — [hw/info/spiflash_map.md](../../../info/spiflash_map.md); скорость записи и время старта — [hw/info/flash_speed.md](../../../info/flash_speed.md).

**Карта флеш** (блок SPIFLASH: «Конфигурация и программа — в этой флеш, загрузка по MSPI», `"fpgaConfig": true`, адрес образа `0x100000`):

| Адрес | Что | Кто читает |
|---|---|---|
| `0x000000` | битовый поток ПЛИС (`hw/impl/pnr/riscv.fs`, у GW1NR-9 — 442 кБайт) | сама ПЛИС при включении питания, импульсе RECONFIG_N, `openFPGALoader -r` |
| `0x100000` | образ программы (64 кБайт) | загрузчик SPIFLASH после сброса системы |
| `0x110000`… | свободная область (`SPIFLASH_USER_ADDR`) — параметры | программа |

Конфигуратор не даёт поставить образ ниже `0x80000` при `fpgaConfig`. В `soc.h` появляется `SPIFLASH_FPGA_CONFIG = 1`, а библиотека не пишет и не стирает ничего ниже `SPIFLASH_USER_ADDR`: ни битовый поток, ни образ.

**Tang Nano 9K.** На плате выводы MODE0 (88) и MODE1 (87) подтянуты к земле резисторами R19 и R17 — это AUTO BOOT, встроенная flash. Режим MSPI включается подтяжкой MODE1 к 1.8 В (`VCCO3_1V8`), например резистором ~1 кОм к контакту R17 со стороны вывода 87: делитель с R17 = 4.7 кОм даёт ≈1.5 В — уверенная 1 для LVCMOS18. DUAL BOOT (`110`: сначала внешняя флеш, при ошибке — встроенная) в корпусе QN88 недоступен: вывода MODE2 нет, а невыведенные выводы MODE заземлены (UG290, табл. 5‑1, примечание [1]). Значит, при MSPI запасного варианта во встроенной flash нет. Но JTAG от MODE не зависит: загрузка SRAM и запись флеш через openFPGALoader работают всегда, и при испорченной флеш плату можно восстановить.

После конфигурации выводы MSPI (59–62) отдаются контроллеру SPIFLASH: генератор ставит «Use MSPI as regular IO». Вывод RECONFIG_N нельзя занимать как I/O — он нужен для перезапуска конфигурации (UG290, §7.5.5).

**Запись.** Внешний инструмент Eclipse **«riscv SPI-FLASH»** (`fpgaload.py spiflash`):
1. битовый поток `hw/impl/pnr/riscv.fs` с адреса 0 — без программы в BSRAM, программа приходит из образа. Битовый поток **пропускается, если не менялся** с прошлой записи (хеш в `fw/Debug/riscv_extflash_cfg.sha256`; `--force` — записать всё равно). С исправленным openFPGALoader (`sdk/openfpgaloader`) запись 442 кБайт — около 3 мин, со стандартным — около 10 мин: у GW1N openFPGALoader побитно управляет выводами флеш через boundary scan и упирается в USB ([sdk/openfpgaloader/README.md](../../../../sdk/openfpgaloader/README.md));
2. образ программы с адреса `0x100000`;
3. `openFPGALoader -r`: ПЛИС заново конфигурируется — из внешней флеш, загрузчик копирует программу.

Обычный цикл «изменил программу → записал» (битовый поток не менялся) — около 3 с; с битовым потоком — 176 с (было 586 с со стандартным openFPGALoader). Поэтому запись из Eclipse обычно занимает секунды: в консоли — «Конфигурация ПЛИС во внешней флеш не менялась - пропуск». Три минуты уходят только после пересборки ПЛИС, после очистки SPI-флеш (она удаляет и отметку о записанном битовом потоке) или с флажком «записать битовый поток, даже если он не менялся» (`--force`).

**Очистка** (`fpgaload.py erase-spiflash`, «Программатор ПЛИС» → «Очистить SPI-флеш», ~1 с): стирается вся флеш (Chip Erase) — битовый поток, образ и данные программы. В режиме MSPI ПЛИС после этого не загрузится, пока флеш не записать заново (~3 мин). Встроенная flash стирается отдельно (`erase-flash`); при MSPI это ни на что не влияет.

Не оставляйте флеш в глубоком сне (`SPIFLASH_PowerDown`) перед перезапуском конфигурации: блок конфигурации ПЛИС, в отличие от нашего загрузчика, может не послать команду пробуждения.

**Проверено на плате** (02.10.2026, Tang Nano 9K с подтяжкой MODE1):
- битовый поток с адреса 0 и образ примера 7 с `0x100000` записаны openFPGALoader'ом;
- после `-r` ПЛИС сконфигурировалась из внешней флеш: `BOOT = 0x05C7_0001`, образ взят с `0x100000`. Старый битовый поток во встроенной flash ищет образ с адреса 0 и дал бы «образа нет» — значит, загружен новый, из внешней флеш;
- UART: «Загрузка: программа из флеш, образ 5916 Байт», счётчик запусков в `0x110000`;
- отладка: `reset halt` → PC = 0, `compare-sections .text` совпадает, `stepi`, точки останова, `finish`, переменные; `reset run` — программа снова из флеш; программа, загруженная отладчиком в память (`restore`), работает;
- защита: стирание и запись по адресам 0, `0x100000`, `0x10FFFE` — `SPIFLASH_ERR_PROTECT`; в свободной области — `SPIFLASH_OK`; за концом флеш — `SPIFLASH_ERR_ADDR`;
- три способа хранения (02.10.2026, исправленный openFPGALoader): SRAM — 4 с, `BOOT = 0` (загрузчик выключен), отладка с `restore`; внешняя флеш — 176 с с битовым потоком и 3 с без него, `BOOT = 0x05C7_0001`, отладка без загрузки и `reset run`. Встроенная flash записывается (12 с), но с поднятым MODE1 ПЛИС с неё не стартует — её загрузку нужно проверять с MODE1 = 0.

## Регистры

| Смещение | Имя | Доступ | Биты | Смысл |
|---|---|---|---|---|
| `0x00` | `CTRL` | чтение/запись | `[0] cs` | удерживать CS: кадр из нескольких обменов |
| | | | `[1] rdauto` | чтение `DATA` запускает следующий обмен 4 байтами |
| `0x04` | `STAT` | чтение | `[0] busy` | идёт обмен или пауза CS — ждать перед запуском |
| | | чтение, запись 1 | `[1] ovr` | обмен запущен при `busy = 1` и пропущен |
| `0x08` | `DIV` | чтение/запись | `[7:0]` | SCK = f_clk / (2 · (DIV + 1)) |
| `0x0C` | `DATA` | запись `sb`/`sh`/`sw` | `[7:0]`/`[15:0]`/`[31:0]` | обмен 1, 2 или 4 байтами, младший байт первым |
| | | чтение | `[31:0]` | принятые байты на тех же местах (байт, принятый при передаче байта k, — в байте k), остальные 0 |
| `0x10` | `BOOT` | чтение | `[2:0]` | итог загрузки: 0 — загрузчик выключен, 1 — программа загружена, 2 — образа нет, 3 — ошибка контрольной суммы, 4 — ошибка разметки |
| | | | `[31:16]` | слов образа прочитано (при ошибке — номер слова, на котором она найдена) |
| `0x100`…`0x1FC` | `WIN` | как `DATA` | | окно `DATA` на 64 слова (страница флеш): копирование блоком (`memcpy`, System Bus отладчика) идёт через `DATA` |

Обмен всегда начинается с младшего байта `DATA`: записи байта и полуслова делаются по адресу `DATA` (`0x0C`), стробы задают только число байт.

**Кадр CS.** При `CTRL.cs = 0` каждый обмен — отдельный кадр: CS опускается на время обмена (так делаются короткие команды: `0x06`, `0x05` + байт ответа, `0x9F` + 3 байта ID, команда с адресом). Для длинных команд (запись страницы, чтение) программа ставит `CTRL.cs = 1`, делает несколько обменов и сбрасывает `cs`: CS поднимается после последнего обмена. После подъёма CS держится пауза 3 такта (`busy = 1`) — время tSHSL флеш.

**Автозапуск чтения** (`rdauto`): чтение `DATA` отдаёт принятые 4 байта и сразу запускает обмен следующими 4. Так чтение массива — одна загрузка `lw` на слово (плюс ожидание `busy`). Первое чтение после команды `0x03` отдаёт ответ на саму команду — его отбрасывают.

**Время.** SCK генерируется из такта шины; MOSI меняется со спадом SCK, MISO берётся в момент следующего спада (поздний отсчёт: запас на задержки выводов и флеш — полный период SCK). Обмен n байтами длится 16 · n · (DIV + 1) тактов. Во время загрузки программы регистры программе недоступны (ядро в сбросе).

После сброса: `CTRL = 0`, `STAT = 0`, `DIV = DIV_INIT`.

## Библиотека на Си (`spiflash.h`)

Адреса областей флеш — из `soc.h` (их считает конфигуратор по настройкам блока):

| Имя | Смысл |
|---|---|
| `SPIFLASH_SIZE` | объём флеш |
| `SPIFLASH_FPGA_CONFIG` | флеш хранит и конфигурацию ПЛИС с адреса 0 (режим MSPI) |
| `SPIFLASH_BOOT`, `SPIFLASH_BOOT_ADDR`, `SPIFLASH_BOOT_SIZE` | загрузка включена; область образа программы (64 кБайт) |
| `SPIFLASH_USER_ADDR`, `SPIFLASH_USER_SIZE` | свободная область — для данных программы |
| `SPIFLASH_DIV_DEFAULT`, `SPIFLASH_SCK_HZ` | делитель после сброса и частота SCK |

| Функция | Действие |
|---|---|
| `SPIFLASH_Init(div)`, `SPIFLASH_InitDefault()` | делитель SCK, выход флеш из сна |
| `SPIFLASH_ReadID()` | JEDEC ID: `0x856016` — PUYA P25Q32U |
| `SPIFLASH_ReadStatus()`, `SPIFLASH_WaitReady(ms)` | регистр состояния (`WIP`, `WEL`); ожидание конца записи/стирания |
| `SPIFLASH_Read(addr, buf, len)` | чтение любой длины |
| `SPIFLASH_Write(addr, buf, len)` | запись любой длины (страницы делятся сами); область должна быть стёрта |
| `SPIFLASH_EraseSector(addr)`, `SPIFLASH_EraseBlock(addr)`, `SPIFLASH_Erase(addr, len)` | стирание 4 кБайт, 64 кБайт, всех секторов области |
| `SPIFLASH_PowerDown()`, `SPIFLASH_WakeUp()` | глубокий сон флеш и выход из него |
| `SPIFLASH_BootStatus()`, `SPIFLASH_BootWords()` | итог загрузчика и размер образа |
| `SPIFLASH_Select/Deselect`, `SPIFLASH_Xfer8/16/32`, `SPIFLASH_CmdAddr` | нижний уровень: кадры и обмены для своих команд |

Запись и стирание ниже `SPIFLASH_USER_ADDR` (образ программы и, в режиме MSPI, конфигурация ПЛИС) функции не выполняют (`SPIFLASH_ERR_PROTECT`), пока `SPIFLASH_PROTECT_BOOT = 1`. Флеш NOR: запись только сбрасывает биты, поэтому перед перезаписью сектор стирают (до ~0.3 с, функции ждут). Ресурс стирания — порядка 100 000 циклов на сектор.

## Пример

Пример 7 в `fw/Core/Src/main.c`: итог загрузчика, ID флеш и счётчик запусков в свободной области флеш (UART, 115200).

```c
#include "spiflash.h"

typedef struct { uint32_t magic, boots, check; } Params;
Params p;
SPIFLASH_InitDefault();
SPIFLASH_Read(SPIFLASH_USER_ADDR, &p, sizeof p);
if (p.magic != 0x314D5250U || p.check != ~p.boots) { p.magic = 0x314D5250U; p.boots = 0; }
p.boots++; p.check = ~p.boots;
SPIFLASH_EraseSector(SPIFLASH_USER_ADDR);
SPIFLASH_Write(SPIFLASH_USER_ADDR, &p, sizeof p);
```

Своя команда флеш — нижним уровнем, например чтение регистра состояния 2 (`0x35`):

```c
uint32_t sr2 = SPIFLASH_Xfer16(0x35U) >> 8;     //Байт 0 - команда, байт 1 - ответ
```

## Тест (`tb_spiflash.sv`)

65 проверок, два контроллера (с загрузчиком и без) и две модели флеш:
- значения после сброса, обмен байтом, полусловом и словом, JEDEC ID, регистр состояния, `WREN`/`WRDI`;
- флаг `ovr`: запуск при `busy` и в паузе CS после кадра — обмен не выполняется и не сливается с прошлым кадром;
- стирание сектора, запись страницы через окно `0x100`, неполная страница, повторная запись (биты только сбрасываются), чтение с автозапуском, в том числе через границу страниц;
- делитель SCK: период 2 и 8 тактов, чтение на наибольшей частоте;
- монитор линий SPI: режим 0, MOSI выставлен не меньше чем за такт до фронта SCK, CS опускается раньше первого фронта, пауза CS не меньше 3 тактов; модель флеш проверяет протокол (CS на границе байта, команды во время записи, запись без `WEL`);
- загрузчик: образ из двух сегментов (запись в память — только во втором чтении), образа нет, испорченная контрольная сумма, неверный признак, адрес вне IMEM/DMEM, невыровненный адрес, слишком длинный сегмент и образ — во всех ошибочных случаях записей нет; флеш в глубоком сне перед сбросом; запись программы во время загрузки игнорируется.

Загрузка в составе процессора проверяется тестами ядра: `py hw/sim/run_tests.py --boot` — все тестовые программы (и сценарий отладчика со сбросом-остановом) записываются образом в модель флеш на порту `bus_per`, и ядро получает их только через загрузчик ([hw/sim/README.md](../../../sim/README.md)).
