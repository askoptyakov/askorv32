openFPGALoader 1.1.1 с ускоренной записью и очисткой флеш GW1N (askoRV32)
=========================================================================

Изменённая версия [openFPGALoader](https://github.com/trabucayre/openFPGALoader) v1.1.1 (выпуск 11.03.2026). Отличается от исходной двумя исправлениями для ПЛИС Gowin GW1N (GW1N-9, GW1NR-9 и др.):
- запись внешней SPI-флеш в ~3.5 раза быстрее (`gowin_spi_flush.patch`);
- работает очистка `--bulk-erase`: встроенной flash и всей внешней флеш (`gowin_gw1n_erase.patch`); в исходной версии для GW1N — «bulk erase flash not supported».

Всё остальное (SRAM, встроенная flash, другие ПЛИС и кабели) работает как в исходной версии.

| Файл | Что это |
|---|---|
| `bin/openFPGALoader.exe` + 7 DLL | готовая программа для Windows x64; работает без MSYS2 (библиотеки рядом). Её берёт `sw/fpgaload/fpgaload.py` |
| `gowin_spi_flush.patch` | ускорение записи внешней флеш, изменения относительно v1.1.1 (`git apply`) |
| `gowin_gw1n_erase.patch` | очистка флеш GW1N, накладывается после первого |
| `build.sh` | сборка из исходников в MSYS2: клонирует v1.1.1, накладывает оба патча, собирает, кладёт результат в `bin/` |
| `../openFPGALoader-1.1.1-askorv32-src.zip` | исходники v1.1.1 с наложенными патчами (локально, в git не хранится — как установщики в `sdk/`) |

## Зачем

На Tang Nano 9K битовый поток ПЛИС (442 кБайт) записывался во внешнюю флеш почти 10 минут, а частота JTAG на время не влияла: 16 кБайт — 21.4 с и при 3, и при 6 МГц. Значит, время уходило не на сам JTAG.

## Как openFPGALoader пишет внешнюю флеш GW1N

У GW1N к флеш нет прямого пути из JTAG. openFPGALoader стирает конфигурацию ПЛИС и управляет выводами MSPI через регистр boundary scan (команда JTAG `0x16`, 8-битный регистр: SCK, CS#, DI, DO и маска направления). Один бит SPI — два сдвига DR:
1. SCK = 0, на DI — значение бита (`spi_gowin_write(&t, NULL, 8)`);
2. SCK = 1 — флеш защёлкивает бит (`spi_gowin_write(&t, &r, 8)`, при чтении отсюда берётся бит DO).

Каждый сдвиг DR — переход в Shift-DR, 8 бит, выход через Exit1-DR и Update-DR (тогда значения появляются на выводах) и 6 тактов TCK в Run-Test/Idle. У Gowin GW2A и GW5A есть свои быстрые пути: весь буфер одним сдвигом, через мост в ПЛИС. У GW1N — только этот, побитный.

## Что было не так

Команды MPSSE (язык FTDI-совместимого программатора) копятся в буфере и уходят по USB пачкой при `flush()` или переполнении. Каждая пачка — это транзакция USB туда и обратно, около 0.1–0.2 мс на программаторе BL702. В исходном коде буфер сбрасывался дважды на **каждый** бит SPI, даже при записи, когда читать нечего:

1. `src/gowin.cpp`, `Gowin::spi_put` (ветка GW1N): после второго сдвига стоял безусловный `_jtag->flush()`;
2. `src/ftdiJtagMPSSE.cpp`, `FtdiJtagMPSSE::writeTDI`: при выходе из Shift-DR последним битом без чтения (`last == 1`, `tdo == NULL`) вызывался `mpsse_write()` — отправка буфера.

Итог — ~165 мкс на бит SPI при любой частоте TCK, то есть ~0.75 кБайт/с. В текущей master-ветке openFPGALoader (10.2026) то же самое.

## Что изменено (`gowin_spi_flush.patch`, 3 файла, +16/−2 строки)

**`src/ftdiJtagMPSSE.hpp`** — объявлен глобальный флажок:
```cpp
extern bool ofl_defer_tdi_flush;   //true: writeTDI не сбрасывает буфер при выходе из Shift-xR без чтения
```

**`src/ftdiJtagMPSSE.cpp`** — определение флажка (`false` по умолчанию) и условие в `writeTDI`:
```cpp
    } else if (_ch552WA) {          //обход для кабелей на CH552 - без изменений
        ...
-   } else {
+   } else if (!ofl_defer_tdi_flush) {
        mpsse_write();
    }
```
Пока флажок не поднят, поведение прежнее — для всех ПЛИС и всех вызовов.

**`src/gowin.cpp`, `Gowin::spi_put` (ветка GW1N)**:
- перед циклом по битам: `ofl_defer_tdi_flush = (rx == NULL);` — отложенная отправка только для записи без чтения;
- после второго сдвига бита: `_jtag->flush();` → `if (rx) _jtag->flush();` — при чтении бит DO нужен сразу, при записи — нет;
- перед завершающим `flush()` (CS# вверх): `ofl_defer_tdi_flush = false;`.

Теперь при записи команды MPSSE для сотен бит копятся в буфере и уходят большими пакетами. Буфер отправляется при заполнении (`FTDIpp_MPSSE::mpsse_store`) и обязательно — в конце каждой команды SPI (подъём CS#), так что порядок и содержимое того, что видит флеш, не меняются: меняется только то, как команды нарезаны на транзакции USB. Чтение (`--dump-flash`, `--verify`, опрос регистра состояния) идёт как раньше, побитно.

## Очистка флеш GW1N (`gowin_gw1n_erase.patch`, 3 файла, +36/−3 строки)

В исходной версии `--bulk-erase` для GW1N печатает «bulk erase flash not supported» и при этом завершается с кодом 0. Исправление:

**`src/gowin.hpp`, `Gowin::bulk_erase_flash()`**:
```cpp
-   if (is_gw5a || is_gw2a)
+   if (is_gw5a || is_gw2a || _external_flash)
        return SPIInterface::bulk_erase_flash();
-   printError("bulk erase flash not supported"); return false;
+   return eraseEmbeddedFlash();
```
- `--external-flash --bulk-erase` — общий путь `SPIInterface::bulk_erase_flash()`: доступ к выводам флеш через boundary scan (как при записи), проверка защиты, команда Chip Erase (`0x60`), ожидание по регистру состояния, перезапуск ПЛИС (`RELOAD`). Для GW1N этот путь был, но не вызывался;
- `--bulk-erase` без `--external-flash` — новый `Gowin::eraseEmbeddedFlash()` (`src/gowin.cpp`): та же последовательность, что в начале `programFlash()` (запись встроенной flash) — `CONFIG_DISABLE`, проверка `GOWIN_VLD`/`POR`, стирание SRAM, `enableCfg`, `eraseFLASH`, `disableCfg` — без записи, затем `RELOAD`.

**`src/main.cpp`**: при ошибке `bulk_erase_flash()` программа завершается с `EXIT_FAILURE` (раньше результат не проверялся) — по коду завершения `fpgaload.py` и Eclipse видят ошибку.

Проверено на плате 02.10.2026 (`fpgaload.py erase-flash`, `erase-spiflash`): встроенная flash — ~1 с; внешняя флеш P25Q32U целиком — ~0.5 с, чтение `--dump-flash` с адресов `0x000000`, `0x100000`, `0x200000`, `0x3FFF00` — везде `0xFF`.

## Скорость (Tang Nano 9K, программатор BL702, флеш P25Q32U, 02.10.2026)

| | исходный | исправленный |
|---|---|---|
| 16 кБайт | 21.4 с | 6.7 с |
| 64 кБайт | ~90 с (оценка) | 26 с |
| битовый поток 442 кБайт + образ программы (`fpgaload.py spiflash --force`) | 586 с | 176 с |
| только образ программы (6 кБайт) с перезапуском ПЛИС | 8 с | 3 с |

Теперь запись упирается в USB: время одно и то же при JTAG 1.5, 3 и 6 МГц. BL702 — устройство USB full speed, а на бит SPI уходит ~30 байт команд MPSSE (два перехода в Shift-DR, данные, выход, Update-DR, 6 тактов). Пути дальнейшего ускорения — в [hw/info/flash_speed.md](../../hw/info/flash_speed.md).

Проверено на плате: битовый поток и образ, записанные исправленной версией, загружаются (ПЛИС стартует из внешней флеш, загрузчик askoRV32 берёт программу).

## Сборка

Нужен MSYS2 (`C:\msys64`, установлен 02.10.2026) с пакетами:

```
pacman -S --needed git mingw-w64-ucrt-x86_64-{gcc,cmake,ninja,pkgconf,libftdi,libusb,hidapi,zlib}
```

Затем из PowerShell:

```
$env:MSYSTEM='UCRT64'; C:\msys64\usr\bin\bash.exe -l /c/GitHub/askorv32/sdk/openfpgaloader/build.sh
```

Скрипт берёт исходники v1.1.1 с GitHub во временную папку, накладывает оба патча, собирает (cmake + Ninja; пути MSYS2 `/ucrt64/...` в `build.ninja` заменяются на `C:/msys64/ucrt64/...` — иначе Ninja и gcc под Windows их не находят) и кладёт `openFPGALoader.exe` с библиотеками в `bin/`. Сборка из архива исходников — то же без шагов `git clone` и `git apply`.

## Отправить авторам

Оба исправления годятся и для исходного проекта: они не меняют протокол и затрагивают только флеш GW1N. Перед отправкой стоит заменить глобальный флажок на метод интерфейса JTAG (например, `JtagInterface::setDeferFlush(bool)`), чтобы не было глобального состояния.
